# PERIPH-EXTRACT-01D — Schema & Cross-Language Conformance

Status: 01D source-only candidate, no operational acceptance. [01E.1 durable recovery](DURABLE-RECOVERY.md) supersedes the earlier production epoch/quarantine limitations while preserving the shared fixture profile. Baseline: 01C `e4dba4e92e2ece152d7f06a8a3ce6b3c10582101`. Original seven candidate schema bytes, identifiers and five historical fixtures remain unchanged. No canonical promotion or new privileges.

## Three distinct validation layers

1. **Wire** — Draft 2020-12 metaschema and instance validation of all seven contracts, with RFC 3339 date-time checks enabled. Python host request, allowlist and response boundaries now use the real local validator. Schema documents are local, immutable and contain no references; no external resolver or live data. Existing strict JSON decoding and local frame budgets remain. Direct requirements are pinned (jsonschema 4.23.0, rfc3339-validator 0.1.4); transitive lock, vendoring/packaging and supply-chain review remain 01E. Missing dependency/config fails closed. Schema validation does not authenticate the peer or authorize any command.
2. **Domain** — Rust uses typed models and pure semantic checks; it is not a raw JSON API or a second host broker. Python retains semantic guards (exclusive ownership, exact IDs, request/reply identity, revisions and disposition/target). A schema-valid message may be rejected by semantic policy. Rust admission continues to check descriptor capabilities, stream semantics, declared binding and control availability.
3. **Host** — Python broker enforces local same-UID peer identity, registered fixed service allowlist, actual USB identity probe, lifecycle, quarantine and bounded replay. No operator delegation or browser control. This phase does not expand host authority.

## Portable corpus

- `conformance/wire-cases.json`: seven complete synthetic baseline documents and 60 named positive/negative vectors; each vector materializes a local copy with explicit set/remove operations. The existing five historical compatibility fixtures are also validated with the full validator. Invalid conditional host request revisions, UUIDs, required nullable fields, nested extra properties, numeric bounds, timestamps, authority fields and service/device shapes are covered.
- `conformance/policy-cases.json`: 32 explicitly expected normalized decisions and reasons. The same corpus drives actual Rust `admit_action` and actual Python `Broker.process` with mocked probes/dispatch. No hardware, systemd or external process runs. Each Python dispatch must be exactly one allowlisted operation; rejection/no-op must dispatch zero. Python replies validate against the unchanged host-response schema. Cases include scope/UUID/revision, missing device/binding, manager unavailable, transitions, idempotent no-op, start/stop of failed/running/stopped services, and revision exhaustion.

### Precisely scoped parity

The corpus uses the **managed USB serial, reviewed fixture registration** profile: one physical descriptor, operator-verified synthetic declaration, both acquisition capabilities, no authorization granted by the fixture, one allowlisted service, no quarantine/replay pending. Rust fixture controls project manager availability and observed presence. Python host IPC has no descriptor/capability/stream/authorization fields; it cannot independently make Rust's domain-only decisions. The actual broker may be stricter due to quarantine, replay, socket peer and allowlist restrictions (01C tests). Domain-only capability, declaration and stream freshness cases remain in the Rust suite. A no-op at an already observed target does not dispatch or imply sensor freshness, verified device identity, authorization, or power state.

Mapping: Rust dispatch permission corresponds to one simulated successful host dispatch (not physical success); AlreadyAtRequestedState corresponds to no_op; typed errors and host error codes normalize to explicit common rejection categories. Unknown/non-installed lifecycle maps to manager_unavailable; stale revisions, identity, malformed UUID, transitions, missing/unverified start device and exhausted revisions are compared separately. We do not claim equivalence of the entire Rust domain and Python host state machines.

The local revision profile is exact integer 0..2^53-1; reject non-integer wire representations at host boundary, out-of-range revisions, and dispatch when the last two revision values would be consumed. Historical JSON Schema permits mathematical integers like 42.0 and larger numbers: this is deliberately stricter runtime policy, not a silent rewrite of the wire schema. Independent epoch seeds remain probabilistic; no durable exactly-once guarantee. Runtime response acceptance requires exact request scope, valid shape, accepted revision strictly greater than the request's revision, no-op equal, and observed target lifecycle. Schema validity alone cannot prove any of these cross-document relationships.

## Acceptance gates

Independent CI now runs source parity, inherited JS regressions, Rust domain + shared vectors, Python host mocks, and full schema/shared-vector tests. Original snapshot provenance remains verifiable; only explicitly adapted broker/CLI/Rust domain files differ. Results must be observed on the exact head. Reproducible release lock/packaging, durable quarantine/recovery, pinned IMU/RI/Console consumer integration, and authorized operator control remain open. No new deployment, installation, start/stop, or robot action. No automatic merge of the Draft.
